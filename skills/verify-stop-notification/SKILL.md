# Verify Stop Notification

通知が必要な状態と配信経路を特定し、設定・送信・受信のどこまで確認できたかを分ける。通知設定の調査だけでは送信や定期タスクの変更を行わない。

## 既存経路を探す

まずプロジェクトの通知処理と運用文書、利用中のスケジューラーの実行コマンド・引数・作業ディレクトリを確認し、参照される設定ファイルと実行結果を追う。設定の所在を調べる前に、既存の秘密値をユーザーへ再提出させない。Webhook URL・トークンは出力しない。

## 通知条件を定める

- 処理失敗、確認待ち、手動停止、正常終了を区別する。未完成であることだけを理由に「人間の判断待ち」としない。
- 通知には、確認できた状態、停止理由、次の行動、利用可能なら対象へのリンクを含める。内部パスや秘密情報を不要に送らない。
- 通知先と送信の許可を依頼内容から確認する。別チャネルへの送信、新しい定期実行、認証・権限変更は別の変更として扱う。

## 疎通と未達の切り分け

1. 設定の存在だけでなく、実行ジョブがその設定を読み込むことを確認する。手動実行と定期実行の環境差を調べる。
2. 許可された疎通試験では、試験であると分かる最小の通知を一度送信し、配信先サービスの応答を確認する。
3. サービスが返した投稿IDやリンクを使って内容と送信先を照合する。取得APIが使えなければ、受信確認は未確認とする。受信端末のプッシュ通知まで確認したと推測しない。
4. 未達なら、ジョブ未起動、設定未読込、送信失敗、配信先違い、端末側通知を順に切り分ける。成功応答のない送信を成功扱いせず、無制限の再送もしない。

Discord Webhookの場合、チャンネルの投稿リンクとWebhookの認証付きURLは別物である。同じWebhookが投稿した既知IDのメッセージは取得できるが、任意のチャンネル履歴を列挙できるとは扱わない。必要なAPI仕様は現行の[Discord公式ドキュメント](https://docs.discord.com/developers/resources/webhook)で確認する。

報告では、設定場所、確認した通知条件、実行結果、サービスへの配信、投稿内容の照合、端末側受信の確認範囲、残る問題を簡潔に示す。
