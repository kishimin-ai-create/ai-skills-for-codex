# Write Article

事実に基づく読みやすい記事を、独立したトピックごとに複数作る。1記事には1つの読者の問い、主張、学びだけを含める。記事数を先に制限せず、十分な根拠がある候補をすべて記事化する。未確認の背景や成果を創作せず、観測事実・推測・提案を明確に分ける。

## 分割と件数

- 変更、コミット、設計判断、テスト、障害、調査結果から記事候補を列挙する。
- 読者の問い、結論、直接の根拠が他の候補から独立している場合は、別の記事にする。
- 同じ結論や根拠を繰り返す候補は統合し、関連記事へのリンクで重複を避ける。
- 件数を増やすための言い換え、根拠の薄い記事、導入だけが異なる記事を作らない。
- ユーザーが件数を指定した場合も、根拠が足りなければ捏造せず、作成できた件数と不足理由を報告する。
- 適格な候補が1件だけなら1記事だけ作り、複数へ分割しなかった理由を報告する。

## 手順

1. 読者、目的、記事タイプ（技術解説、変更記録、障害報告、チュートリアル、比較）、対象範囲、公開可否、言語、長さ、出力先を確定する。出力先の既存記事とファイル命名・連番規約も確認する。
2. 根拠を収集する。変更なら`git log`・`git diff`・関連ファイル・テスト結果・ADR・公式文書を確認し、ログや秘密情報を記事へ転載しない。
3. FACT（直接確認）、INFERENCE（事実からの判断）、PROPOSAL（提案）を分類する。未確認の原因、性能、効果、日付を断定しない。
4. 候補ごとに仮タイトル、読者の問い、主張、根拠、記事タイプ、出力ファイルを一覧化する。既存記事と重複する候補、根拠不足の候補、統合する候補も記録する。
5. 適格な候補をすべて選び、記事の目的に合うテンプレートを「記事テンプレート」から選ぶ。該当するテンプレートがなければ、タイトル、要約、背景、問題、方針、実装、検証、結果、学び、制約・次の課題の順で独立したアウトラインを作る。不要な節は削る。
6. 各記事を個別のMarkdownファイルとして執筆する。コード・コマンド・表・図は再現に必要な最小量だけ掲載し、パス・バージョン・前提・期待出力を明示する。秘密値、個人情報、巨大なログ、著作権上不適切な転載を含めない。
7. 各記事について見出し、段落、用語、コード、リンク、日付、数値を編集する。主語と因果関係を曖昧にせず、変更のHowと理由のWhyを分ける。
8. 各記事を[レビュー checklist](references/review-checklist.md)で確認し、記事群全体でも重複、抜け、矛盾、命名・連番の衝突がないか確認する。必要なら[スタイルガイド](references/style-guide.md)を参照する。
9. MarkdownをTechBlogリポジトリへすべて保存する。ユーザー指定のパスを優先し、連番規約がある場合は次の未使用番号を使い、既存ファイルを上書きしない。
10. 「TechBlogへの公開」手順に従い、記事をコミットして作業ブランチへpushする。
11. 作成した全ファイル、記事ごとの対象範囲と根拠、作成件数、統合・除外した候補と理由、コミット、push先、未確認事項を報告する。保存またはpushしていない記事を公開済みと書かない。

## TechBlogへの公開

1. コミット前にリポジトリルート、`origin`、現在ブランチ、upstream、差分を確認し、対象がTechBlogであることを確定する。
2. 記事と、その記事に必要な日誌の訂正だけをstageする。無関係な変更や生成物を含めない。
3. `git-rules`のコミット規則に従い、記事のWhyが分かる`docs:`コミットを作成する。既に記事が正しくコミット済みなら重複コミットしない。
4. `main`などの共有ブランチ上にいる場合は直接pushせず、`docs/<short-description>`形式の作業ブランチを作成する。
5. 作業ブランチ名と同名のremote refを明示し、forceなしでpushする。upstreamがない場合だけ同名ブランチをupstreamに設定する。
6. ローカルHEADとremote branchのSHAが一致することを確認する。不一致またはpush失敗なら公開済みと報告しない。

pushはTechBlogの記事公開に限定して明示的に許可された処理である。題材となったアプリケーションリポジトリや共有ブランチへ、この手順を流用してpushしない。

## 記事テンプレート

### テンプレート1: Learning Log

新しい技術、ライブラリ、API、ツール、設定などを実際に試し、実現したこと、検証手順、遭遇した問題、理解の変化を記録する場合は、[Learning Log Template](assets/learning-log-template.md)を全文読んで使用する。

- ファイルをそのまま出力先へ複製し、角括弧のプレースホルダーを根拠に基づく内容へ置き換える。
- `前提・環境`には再現に必要な項目だけを残す。
- 実際に遭遇していない問題を`つまずいたところ`へ創作しない。該当しなければ、その旨を短く記載する。
- Step数は実際の検証手順に合わせて増減する。
- 公式資料を実際に参照した場合だけ`参考資料`へ記載する。

### テンプレート2: Troubleshooting

実際に発生したエラーや症状について、調査仮説、確定原因、解決方法、動作確認、再発防止を記録する場合は、[Troubleshooting Template](assets/troubleshooting-template.md)を全文読んで使用する。

- ファイルをそのまま出力先へ複製し、角括弧のプレースホルダーを根拠に基づく内容へ置き換える。
- `結論`では確定した原因と実施済みの解決方法を先に示す。原因未確定なら断定しない。
- 調査中に実際に検討した仮説だけを記載し、後からもっともらしい仮説を追加しない。
- 採用しなかった仮説も、確認方法と否定できた結果に価値がある場合は残す。
- `動作確認`には修正後に実行したコマンドと観測結果だけを書く。
- 再発防止を実施していない場合は、提案を実施済みと表現しない。

### テンプレート3: Design Decision

技術選定や設計判断について、背景、課題、制約、実際に検討した選択肢、評価軸、採用理由、導入後の結果、トレードオフを説明する場合は、[Design Decision Template](assets/design-decision-template.md)を全文読んで使用する。

- ファイルをそのまま出力先へ複製し、角括弧のプレースホルダーを根拠に基づく内容へ置き換える。
- 実際に存在した制約、選択肢、評価軸だけを記載し、議論を後から創作しない。
- 比較表では全Optionを同じ評価軸で比較する。評価できない項目は推測で埋めず、未確認と示す。
- `実装後の結果`は観測済みの結果だけを書く。導入前の記事では未実施であることを明記する。
- 採用案の欠点と残存リスクも省略しない。
- 関連するADRがある場合は参照し、記事を設計判断の正本として扱わない。

### テンプレート4: Guide / Tutorial

読者が手順を順番に実行し、特定の技術を使った完成形へ到達するための記事を書く場合は、[Guide / Tutorial Template](assets/guide-tutorial-template.md)を全文読んで使用する。

- ファイルをそのまま出力先へ複製し、角括弧のプレースホルダーを根拠に基づく内容へ置き換える。
- 冒頭で完成形と読了後にできることを明示する。
- 各Stepは、目的の説明、実行するコードまたはコマンド、実行後の状態の順に書く。
- コマンドの実行場所、前提となる状態、副作用が必要なら明記する。
- `Installation`、`Configuration`、`よくある問題`は実際に必要な場合だけ残す。遭遇していない問題を創作しない。
- 動作確認には実行済みのコマンドと観測結果を記載し、期待値だけを成功結果として扱わない。
- 公式資料を実際に参照した場合だけ`参考資料`へ記載する。

### テンプレート5: Comparison / Evaluation

複数の技術や設計を同じ目的と条件で検証し、評価軸ごとの結果、トレードオフ、条件別の推奨を示す場合は、[Comparison / Evaluation Template](assets/comparison-evaluation-template.md)を全文読んで使用する。

- ファイルをそのまま出力先へ複製し、角括弧のプレースホルダーを根拠に基づく内容へ置き換える。
- Use Case、環境、Version、要件、制約を揃え、比較結果に影響する条件を省略しない。
- 全Optionを同じ評価軸と検証方法で比較する。Optionごとに有利な条件へ変えない。
- 評価軸は比較の目的から定義し、結果を見てから都合よく追加・削除しない。
- 可能な場合は計測値または観測結果を使う。未計測の性能や効果を断定しない。
- 単一の勝者を前提にせず、前提条件ごとに適するOptionと不利になる条件を示す。
- 比較結果を未検証の環境やUse Caseへ無条件に一般化しない。

### テンプレート6: Retrospective / Report

完了した取り組みやプロジェクトについて、当初の目的と想定、実施内容、観測結果、成功・失敗、想定との差、再利用可能な学び、次回の方針をテーマ単位で振り返る場合は、[Retrospective / Report Template](assets/retrospective-report-template.md)を全文読んで使用する。

- ファイルをそのまま出力先へ複製し、角括弧のプレースホルダーを根拠に基づく内容へ置き換える。
- 当初の想定には、開始前に実際に持っていた仮説や期待だけを書く。結果を知った後の想定を創作しない。
- 実際の結果は、数値、テスト、ログ、利用者の反応など観測可能な事実と、そこからの推論を区別する。
- 良かったことだけでなく、失敗、期待未達、都合の悪い結果も残す。
- 想定との差の原因が未確認なら断定せず、確認できた範囲と未確認事項を分ける。
- 学びは感想で終わらせず、次の技術判断や実装で再利用できる条件付きの知見にする。
- 時系列の記録が主目的なら、このテンプレートではなく`techblog-diary`を使用する。

## 記事タイプ別の要点

- 技術解説：概念→最小例→失敗例→検証→適用条件。
- 変更記録：目的→変更前の課題→差分→検証→影響→残存リスク。
- 障害報告：影響→時系列→検出→原因（確定/仮説）→対応→再発防止→未解決。
- チュートリアル：前提→手順→確認→トラブルシュート→撤去/ロールバック。
- 比較：同じ評価軸・入力・環境を揃え、結論の適用範囲を限定する。

## 出力契約

独立した記事候補を可能な限り多く発見し、適格な候補を1トピック1ファイルで全件作成する。記事をTechBlogの作業ブランチへコミット・pushし、remote反映を確認する。作成した記事の一覧、各記事の根拠と検証方法、未確認事項・制約、保存先、コミット、push先を報告する。統合・除外した候補があれば理由を示す。読者に必要な情報を保ったまま簡潔にし、断定できない内容はラベル付きで残す。
