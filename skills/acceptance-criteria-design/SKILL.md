# Acceptance Criteria Design

## 目的

受け入れ条件（AC）を、そのままAcceptance Test（AT）へ変換できる水準へ引き上げる。

ATが浅くなる原因は、多くの場合ATの書き方ではなくACの質にあり、ACの質の問題は要件定義の不足に由来する。
ATを書き直す前にACを、ACを書き直す前に要件を疑う。

## 前提

ACの情報源は2方式のいずれかで、リポジトリが採用している方を使う。

| 方式 | 何を満たせば完成か | なぜ作るか |
| --- | --- | --- |
| ドキュメント方式 | `docs/ACCEPTANCE.md` | `docs/PRD.md` |
| Issue方式 | 対象Issue本文の `## Acceptance criteria` | 同 `## Problem` と `## Proposed solution` |

**リポジトリがどちらを正とするか明示している場合は、それに従い、確認を求めない。**
`CLAUDE.md`、`AGENTS.md`、設計文書のいずれかに記載があればそれが答えである。

明示が無く、かつ両方に受け入れ条件が存在する場合にだけ、ATを書く前に確認する。
真実源が2系統あるまま進めると、実装の根拠が割れるためである。

## 手順

### 1. User Storyを確認する

誰が、何をしたくて、なぜ必要なのかが記述されているかを確認する。
これが無いACは、何を満たせば完成なのかを判定できない。

### 2. 各ACをGiven/When/Thenへ変換する

前提、操作、観測結果の3つに分解する。分解できないACは、複数の条件が混ざっているか、条件ではなく要望である。

### 3. 観測可能性を点検する

Thenが、外部から観測できる結果になっているかを確認する。

| 観測できる | 観測できない |
| --- | --- |
| 画面に表示される内容 | 内部状態の値 |
| APIの応答とステータス | 呼び出された関数 |
| 保存され再訪時に残る結果 | 使用されたクラスやモジュール |
| 操作できる・できない | 実装上の分岐 |

実装の語彙で書かれたACは、実装を追認するテストを生む。ユーザーの語彙へ書き換える。

### 4. 曖昧語を排除する

「適切に」「正しく」「速く」「使いやすく」「安全に」は、判定できる表現へ置き換える。
置き換えられない場合、決まっていない仕様がそこにある。

### 5. 網羅性を点検する

正常系だけでなく、異常系、境界、失敗後の回復が含まれているかを確認する。
特に、失敗したときに何が保たれるのか（直前の成功結果、入力、遷移）が定義されているかを確認する。

### 6. 独立性を点検する

1つのACが1つの判定可能な結果を表しているかを確認する。
「かつ」「および」で複数の結果が結合しているACは分割する。

### 7. 判定する

| 判定 | 次の行動 |
| --- | --- |
| すべて満たす | ATの作成へ進む |
| 一部が不足 | 不足箇所を具体的な質問へ変換し、要件へ差し戻す |
| User Storyが無い | ACではなく要件定義から着手する |

不足を自分の推測で埋めてはならない。推測で埋めたACは、根拠のないATになる。

### 8. 結果を記録する

ACを更新した場合は、source of truthの文書を更新する。ATのコメントや別の場所に写して二重管理にしない。

## チェックリスト

- User Storyに、誰が・何を・なぜが書かれている。
- 各ACがGiven/When/Thenへ分解できる。
- Thenが外部から観測できる結果である。
- 実装の語彙（関数名、クラス名、DOM構造）を含まない。
- 曖昧語が具体的な判定基準へ置き換えられている。
- 異常系と境界が含まれている。
- 失敗時に何が保たれるかが定義されている。
- 1つのACが1つの判定可能な結果を表している。
