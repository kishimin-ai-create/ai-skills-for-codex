# Requirements Definition Writing

ユーザーとの対話を通じて、実装や設計の前提になる検証可能な要件定義書を作る。分からない内容を推測で埋めず、重要な未確定事項は質問して合意を得る。

## 責務境界

- 要件として「何を満たすか」を定義し、実装方法や詳細な構成を決めない。
- ユーザーが指定した技術、法令、サービス、予算、納期は制約として記録する。
- 調査、設計、実装、Issue作成、外部サービスの変更は、別途依頼されない限り行わない。
- 事実、ユーザーが確定した判断、提案、未決事項を混同しない。
- シークレット、認証情報、個人情報、非公開URLなどを文書へ転記しない。必要なら匿名名または設定項目名で表す。
- `Approved` は承認者による明示的な承認がある場合だけ設定する。

## 1. 根拠を集める

ユーザーが提供した資料と、指定された範囲にある既存の要件、Issue、業務資料、コード、テスト、ADRを確認する。確認できた内容を次の4種類に分ける。

| 区分 | 扱い |
| --- | --- |
| 確定 | 根拠またはユーザーの明示回答があり、本文へ記載できる |
| 仮案 | 選択肢として提示できるが、確定事項として記載しない |
| 未決 | ユーザーの判断が必要で、`TBD`として追跡する |
| 対象外 | 今回の要件定義に含めないことが合意されている |

既存資料間で矛盾がある場合は、都合のよい方を採用せず、矛盾する記述と影響する要件をユーザーへ示す。

## 2. 対話で要件を確定する

最初に、判明済みの内容と重要な不足事項を短く整理する。その後、一度に1〜3個の関連する質問を行い、回答を受けてから次の質問へ進む。大量の質問票を一度に提示しない。

質問は、後続の判断を左右する順に扱う。

1. システムの目的、解決する課題、成功の判断基準
2. 対象ユーザー、利用場面、対象範囲、対象外
3. 現行業務、新業務、業務ルール、例外
4. 必須機能、入出力、正常系、異常系、優先順位
5. データ項目、機密性、保持、削除、移行
6. 外部システム、責任分界、障害時の挙動
7. 性能、可用性、信頼性、セキュリティ、プライバシー、法令
8. 運用、監視、バックアップ、復旧、受入条件
9. 文書情報、担当、期限、承認方法

回答が抽象的な場合は、観測または検証できる条件になるまで具体化する。例えば「速い」は目標応答時間と測定条件、「安全」は認証対象、権限、保護対象、失敗時の挙動を確認する。

合理的な選択肢が複数ある場合は、各案の影響を簡潔に示して選択を求める。ユーザーの回答を勝手に拡張せず、回答後に「確定したこと」「残っていること」を短く返す。既に回答された質問を繰り返さない。

次の事項が未確定なら、最終版を完成扱いにせず対話を続ける。

- 目的または主要利用者
- Must機能の範囲
- 重要な業務ルールと例外
- 保護対象データと認証・認可の境界
- 外部連携の責任分界
- 受入可否を判断する条件
- 法令・契約・権利に関する運用可否

ユーザーが判断を保留した項目は推測せず、期限・担当・状態を伴う未決事項へ記録する。ユーザーが未決事項を残したDraftの作成を明示した場合は、Draftとして作成してよい。

## 3. 要件を書く

日本語の要件定義書には [assets/requirements-definition-template-ja.md](assets/requirements-definition-template-ja.md) を使用する。ユーザーが保存先を指定していない場合は、書き込み前に保存先を確認する。

- 要件には一意なIDを付ける。
- 各機能要件は、利用者、前提、入力、処理結果、正常系、異常系、業務ルールが追跡できるようにする。
- 非機能要件は、可能な限り数値、測定条件、測定方法、合否基準を記載する。
- 受入条件はMust要件と対応させ、第三者が合否を判断できる文にする。
- 実装方式、クラス構成、ライブラリ選定、クラウド製品、物理テーブル設計などは、確定した制約でない限り基本設計へ委ねる。
- 該当しない節は理由を付けて「対象外」とする。空欄のまま完成扱いにしない。
- 未決事項は `TBD-xxx` として、内容、担当、期限、状態を記録する。
- ユーザーが指定していない数値、日付、担当者、法的判断を作らない。

## 4. レビューと合意

Draftを提示するときは、少なくとも次を確認する。

- 目的、対象範囲、機能、データ、外部連携、非機能、運用、受入条件が互いに矛盾していない。
- Must要件に対応する受入条件がある。
- 対象外と未決事項が明示されている。
- 業務要件と機能要件の用語が統一されている。
- 認証と認可、バックアップと復旧、ログと監視を混同していない。
- 利用可能であることと、法令・契約上許可されていることを混同していない。
- 要件に不要な実装詳細、秘密情報、根拠のない断定を含んでいない。

レビュー後、重要な変更点と残る未決事項をユーザーへ示し、必要な対話を続ける。ユーザーが内容を確認するまではステータスを`Review`または`Approved`へ変更しない。

## 完了条件

- ユーザーが重要な要件と対象外を確認している。
- Must要件と受入条件を相互に追跡できる。
- 重要な未確定事項が解消されているか、Draftの`TBD`として明示されている。
- 事実、合意事項、未決事項を区別している。
- 保存先、文書ステータス、実行した確認、残留リスクを報告している。
