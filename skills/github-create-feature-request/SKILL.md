# GitHub Feature Request

解決したい課題を中心に機能要望を構成し、明示的に依頼された場合だけGitHubへ起票する。

## 手順

1. 対象リポジトリを確定する。ユーザー指定を優先し、指定がなければ現在のGitリポジトリと`origin`から候補を確認する。候補が複数ある場合は起票前に質問する。
2. 適用される`AGENTS.md`、`.github/ISSUE_TEMPLATE/feature_request.yml`、README、関連ADR、既存機能を読む。リポジトリ固有テンプレートがなければ[機能要望Issue本文](references/issue-template.md)を使う。
3. 要望の背景をコードとドキュメントから確認し、現在の挙動、困っている利用者、発生条件を整理する。未確認の需要、効果、実装難易度を断定しない。
4. タイトル、解決したい課題、提案する解決策を確定する。代替案、補足、受入条件、対象外は根拠がある場合に記載する。不足があり、推測で埋めると方向性が変わる場合だけユーザーへ質問する。
5. GitHubのIssue検索で、課題と提案の特徴的な語を使ってopen Issueの重複を確認する。同じ目的のIssueがある場合は、新規起票せずリンクを返す。別Issueへ分ける明確な理由がある場合だけ続行する。
6. 問題と解決策を分離して本文を作る。特定の実装方法しか認めない要件でない限り、課題を先に説明し、実装の選択肢を残す。秘密情報、個人情報、未確認の数値を含めない。
7. ユーザーが「起票」「作成」「公開」まで明示した場合だけ、接続済みGitHubツールを優先してIssueを作成する。利用できなければ、認証済みのGitHub CLIを使用する。どちらも利用できなければ本文をドラフトとして返し、作成済みと表現しない。
8. `enhancement`ラベルが存在する場合は付与する。ラベルが存在しない場合はIssue作成を優先し、未付与であることを報告する。
9. 作成後にIssue番号、タイトル、状態、URLを再取得して確認し、URLを返す。

## 品質基準

- タイトルが利用者または開発者に可能になることを表す。
- 課題が解決策とは独立して説明されている。
- 提案、代替案、対象外を混同しない。
- 受入条件は観測可能な振る舞いとして書く。
- 未確認の効果や優先度を断定しない。
- Issueを作成した状態とドラフトだけの状態を区別する。

## 出力

- 重複Issueがある場合: 重複候補のURLと判断理由
- 起票した場合: Issueタイトル、番号、URL、付与したラベル
- 起票できない場合: 完成したドラフト、ブロッカー、必要な次の操作
