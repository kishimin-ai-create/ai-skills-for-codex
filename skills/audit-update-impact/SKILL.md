# Audit Update Impact

インストールした場所と、各環境が実際に使う実行物をたどる。手元の更新成功から、本番にも反映されたと推定しない。

## 利用経路を追う

- 更新対象、変更前後のバージョン、対象プロジェクト、調査対象の環境を確定する。会話に出たツールを、製品自身のバージョンと混同しない。
- ローカルの実行パスとバージョンを新しいプロセスで確認し、複数インストールやPATHの優先順位、実行中プロセスに残る古い版を区別する。
- プロジェクトのバージョン固定、ロック、実行スクリプトを読む。システムの実行物、プロジェクト固有環境、ダウンロードされるツールのどれが使われるかを確認する。
- コンテナはベースイメージ、ビルドステージと最終ステージ、コピー・インストール元、ビルド引数を追う。実行時に不要なビルド用ツールを、本番ランタイムへ入れる更新と混同しない。
- CIはジョブごとのインストール方法、固定値、キャッシュ、イメージを確認する。ローカル設定がCIにも継承されると仮定しない。
- 本番は取得可能なデプロイ定義、稼働イメージのID・digest、リリース識別情報、実行時バージョンを照合する。タグ名だけで中身や稼働反映を保証しない。

## 証拠の段階を分ける

| 段階 | 確認できること | これだけでは確認できないこと |
| --- | --- | --- |
| 設定・Dockerfile | 次に解決・ビルドされる版の指定 | 生成イメージや現在稼働中の版 |
| ローカル実行結果 | その環境・実行パスで使われた版 | CIや別コンテナの版 |
| ビルド済み成果物 | 調査した成果物に含まれる版と識別情報 | 本番でその成果物が使われているか |
| 稼働情報 | 調査時点の実行環境・版・成果物 | 未調査の環境や将来の反映 |

「影響なし」には利用経路上で依存しない根拠が必要。「不明」「設定上は変更済み」「実行で確認済み」を区別し、取得不能を最新・安全・反映済みと言い換えない。

## 結果

環境ごとに、管理元、指定版、観測した版、根拠と確認時点、反映状態、必要な次の作業を表で示す。変更の要否は互換性や実際の利用経路から説明し、本番反映の時期・範囲が未決ならその判断を残す。

調査依頼では設定更新、再ビルド、コンテナ再作成、レジストリ公開、デプロイを行わない。稼働確認のためのコマンドも、読み取りで実施できる範囲を選ぶ。取得不能な稼働情報は不足証拠として報告し、調査を口実に本番設定を変えない。
