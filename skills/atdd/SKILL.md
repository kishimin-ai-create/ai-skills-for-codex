# Acceptance Test Driven Development

## 目的

テスト駆動開発をシステム全体へ拡張し、実装を始める前にE2E相当の受け入れテスト（AT）を固定する。

AIは「テストが通る」という報酬シグナルに対して最適化する。実装を行う主体がテストへ到達できる限り、実装を直すより
テストを改変するほうが安い経路として残り続ける。禁止を指示しても、この経路自体は消えない。

ATを実装主体の到達範囲の外へ置くことで、「テストが通った」を再び根拠として使えるようにする。

## 適用範囲

適用する。

- ユーザーが外部から観測できる振る舞いを追加または変更する作業。
- 複数の部品にまたがる作業、または品質が重要な作業。

適用しない。この場合は内側のループ（`tdd` Skill）だけを適用する。

- 外部から観測できる振る舞いを持たない作業（ツールチェーン整備、設定変更、内部リファクタリング）。
- 使い捨てのプロトタイプや、単一ページの静的な成果物。

判断できない場合は、ATを書けるかどうかで判定する。書けないのであれば、方法論ではなく要件が不足している。

## 手順

### 1. 受け入れ条件を検証する

ATDDの入力は次の2つである。どちらかが無い場合は、ATを書かずに不足を報告して止まる。

| 文書 | 内容 |
| --- | --- |
| `docs/PRD.md` | なぜこの機能が必要か、どのユーザー要求に応えるか |
| `docs/ACCEPTANCE.md` | User Storyと、それぞれの受け入れ条件（AC） |

`acceptance-criteria-design` Skill を適用し、受け入れ条件（AC）がATへ変換できる水準かを確認する。

満たないACからATを書いてはならない。浅いATは、ATDDの失敗ではなく要件定義の不足として現れる。
不足している場合は、ATを書かずに要件へ差し戻す。

### 2. ATを作成する（Outer Red）

- 1 User Story に対して1本のATを作成する。複数のACは同一AT内の検証で網羅し、どのACが壊れたかは検証名で区別する。
- リポジトリ直下の `acceptance/` へ配置する。この配置がATの識別子であり、保護の対象範囲である。
- ファイル名は、リポジトリのテストサイズ規約（`.small.test.ts` / `.medium.test.ts` / `.large.test.ts`）に従う。
  サイズは「ATだから」ではなく、実際に使用する依存範囲で判定する。
- ユーザーの操作と観測結果だけで記述する。内部モジュール名、実装関数、DOM構造に依存させない。
- 実装コードを書いてはならない。
- ATが失敗することを確認する。失敗の理由が未実装であること、構文エラーや環境不備ではないことを確認する。

### 3. ATを確定する

`test:` プレフィックスでATをコミットし、そのコミットのSHAを記録する。このSHAが、以降の検証の基準点になる。

コミットした時点でATはロックされる。以降、`acceptance/` 配下のコミット済みファイルへのEdit・Writeは拒否される。
`git add` しただけの状態はまだロックされないため、Outer Redの推敲は妨げられない。

### 4. 内側のループを回す（Inner TDD）

`tdd` Skill に従い、Unit Test → 実装 → Refactor を1項目ずつ繰り返す。

このフェーズでは `acceptance/` を読んでよいが、変更してはならない。ATが通らない場合に直すのは常に実装側である。

内側の設計手法はTDDに限定しない。ATが実装から隔離されている限り、内側の進め方は選択してよい。

### 5. Outer Greenを確認する

以下をすべて満たしたときにのみ、ATがGreenになったと扱う。

1. ATが成功している。
2. `acceptance/` に未コミットの変更がない。

   ```sh
   git status --porcelain -- acceptance/
   ```

3. AT確定コミット以降、`acceptance/` に差分がない。

   ```sh
   git diff --name-only <AT確定コミットのSHA>..HEAD -- acceptance/
   ```

どちらかが空でない場合、そのGreenは根拠にならない。ATを確定時点へ戻し、差分が生じた理由を報告する。

### 6. 次のATへ進む

テストリストが空になるまで、ステップ2から繰り返す。

## ATを変更してよい唯一の場合

要件そのものが変わったときだけ、ATを変更してよい。実装を通すために変更してはならない。

1. ユーザーの承認を得る。
2. リポジトリ直下に `.atdd/unlock` を作成し、どのACがなぜ変わったかを記述する。
3. ATを変更し、`test:` でコミットする。新しいSHAを基準点として記録し直す。
4. `.atdd/unlock` を削除する。

`.atdd/unlock` を残したまま実装フェーズへ進んではならない。保護が外れたままになる。

## 自律ループ（`/goal`）

Outer と Inner の往復をユーザーが毎ターン促さずに回す場合、`/goal` を使う。毎ターンの終了時に
小型モデルが条件の充足を判定し、未達ならそのまま次のターンへ進む。`/goal` はユーザーが入力する
コマンドであり、Agentからは設定できない。

条件は次の3つを含める形で書く。判定モデルはコマンドを実行せずファイルも読まないため、
**会話に現れた出力だけで判定できる条件**にしなければならない。

1. 測定可能な終了状態
2. それをどう示すか（実行するコマンドと期待する終了コード）
3. 途中で変えてはならないもの

ATDDでの雛形。

```text
/goal Issue #<番号> の受け入れ条件をすべて満たす。
確認方法: bun run lint、bun run typecheck、bun run test:coverage:pr、
bun run e2e:<size> をこのセッションで実行し、いずれも終了コード0であることを出力で示す。
不変条件: 実装フェーズで acceptance/ 配下を変更しない。毎ターン
git status --porcelain -- acceptance/ と
git diff --name-only <AT確定コミット>..HEAD -- acceptance/ が空であることを出力で示す。
30ターンを超えたら停止する。
```

注意点。

- 判定は会話の内容に対して行われる。検証コマンドを実行して**その出力をターン内に残す**こと。
  「通ったはず」と述べるだけでは、判定モデルはそれを根拠にできる。必ず実行結果を示す。
- Agentをバックグラウンドで実行している間、そのターンの判定は見送られる。atdd-agentが
  tdd-agentを起動する構成では判定の間隔が延びる。
- 無人で回すにはauto modeが要る。既定の権限モードでは許可されていないツール呼び出しで停止する。
- 条件は4000文字まで。ターン上限の節を入れないと、達成も不能判定もされない限り回り続ける。

`/goal` はhooksの仕組みの上に実装されているため、`disableAllHooks` が有効だと使用できない。
