# T-Wadaの原則でテストをレビューする

テストを単なる確認コードではなく、振る舞いを記述し設計を前進させる道具としてレビューする。本人由来の原則と一般的なテスト品質基準を混同しない。

## 必須参照

レビュー前に [references/principles.md](references/principles.md) を最後まで読む。直接確認できない見解をT-Wadaの主張として扱わない。

## ワークフロー

1. 対象のテスト、テスト計画、関連する仕様・ADRを読む。
2. 実装済みテストでは、対象の公開境界とテスト設定も確認する。内部実装だけから期待値を作らない。
3. 各ケースが表す期待する振る舞いを一文にする。一文にできなければ責務過多または意図不明として調べる。ただし、一操作から生じる不可分な複数結果を機械的に分割しない。
4. 「T-Wada由来の観点」と「一般的なテスト品質」の順に評価する。
5. 実害のある指摘だけを、根拠と最小の改善案を添えて報告する。依頼がレビューのみなら編集しない。

## T-Wada由来の観点

### テストリスト

- 望まれる振る舞いが列挙され、作業単位へ分解されているか。
- 正常系、境界、失敗を無目的に網羅せず、仕様上の差があるケースを残しているか。
- 新たに判明した振る舞いを追加できる生きたリストになっているか。

### Red

- まだ満たされていない振る舞いに対して失敗するか。
- 失敗理由が予想どおりで、設定不備や別の障害による偽のRedではないか。
- 一度に導入する振る舞いが小さく、失敗から次の実装判断が明確か。

### Green

- テストが要求する振る舞いを満たす最小の変更へ導くか。
- 特定の入力だけをハードコードして不当にGreenにできる場合、次の具体例による一般化がテストリストにあるか。
- テスト自身が不要な実装方式を指定していないか。

### Refactor

- 外部から観測できる振る舞いを守り、内部設計を安全に変更できるか。
- private関数、呼出し順、内部状態などへの結合が、リファクタリングを不必要に妨げていないか。
- テストコードにも重複や意図を隠す仕掛けがなく、次のサイクルを短く保てるか。

## 一般的なテスト品質

以下は有用な補助基準だが、T-Wada固有の主張として帰属させない。

- テスト名と期待値が利用者または呼出し側から観測可能な契約を表す。
- 主要な結果をassertし、単に「例外が出ない」「mockが呼ばれた」だけで契約を代用しない。
- テスト間で可変状態を共有せず、単独・任意順で再現できる。
- 時刻、乱数、network、filesystemなどの非決定要因を境界で制御する。
- test doubleは境界に置き、実装詳細の再現装置にしない。
- 同じ契約を重複検証するケースや、異なる契約を一つに詰め込むケースを識別する。

## Findingの基準

- `MUST_FIX`: テストが誤った理由で成功・失敗する、契約違反を見逃す、非決定的、順序依存など、偽の安心を生む。
- `SHOULD_FIX`: 実装詳細への過剰結合、意図不明、重複など、変更容易性や診断性を継続的に損なう。
- `QUESTION`: 仕様や証拠が不足し、判断によって期待する振る舞いが変わる。推測で欠陥扱いしない。

好みだけの書式差、根拠のない網羅要求、既に別層で十分に保証された重複ケースはFindingにしない。

## 出力形式

```markdown
## 判定
レビュー対象と総評を1〜3文で記載する。

## Findings
### [MUST_FIX|SHOULD_FIX|QUESTION] 要点
- 根拠: ファイル・ケース・具体的な挙動
- 観点: T-Wada由来 / 一般的なテスト品質
- 影響: 何を見逃すか、何が変更困難になるか
- 最小の改善: 最も小さい修正または確認事項

## 良い点
維持すべき具体的な判断を簡潔に記載する。

## 保証範囲
保証できる振る舞いと、未保証だが仕様上必要と確認できた振る舞いを区別する。
```

重大なFindingがなければ「重大な問題は見つからない」と明記する。件数を水増ししない。

## 証拠がない場合

- `test.todo`や計画だけなら、テストリストの妥当性と実行時の保証を分ける。「計画は妥当だが現在の保証はない」は矛盾しない。
- test body、実装、実行結果がなければRedの失敗理由やGreenの最小性を「評価不能」とする。証拠不足をFindingへ変換しない。
- 開発順序の評価を依頼されていない限り、Git履歴まで調査範囲を広げない。現在のsnapshotで確認できることだけを述べる。
- `QUESTION`は仕様判断への回答が必要な場合に使う。単なる未実装や未実行は保証範囲の制約として記載する。
