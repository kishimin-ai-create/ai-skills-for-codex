# GitHub Bug Issue

観測した事実から再現可能な不具合報告を作り、明示的に依頼された場合だけGitHubへ起票する。

## 手順

1. 対象リポジトリを確定する。ユーザー指定を優先し、指定がなければ現在のGitリポジトリと`origin`から候補を確認する。候補が複数ある場合は起票前に質問する。
2. 適用される`AGENTS.md`、`.github/ISSUE_TEMPLATE/bug_report.yml`、関連ADR、既存テスト、エラーログを読む。リポジトリ固有テンプレートがなければ[不具合Issue本文](references/issue-template.md)を使う。
3. 現象を安全に再現できる場合は再現し、コマンド、環境、結果を記録する。再現していない情報は「未確認」と明記する。調査依頼だけならコードを変更しない。
4. タイトル、現象、再現手順、期待する動作を確定する。ブラウザ固有の問題なら対象ブラウザも確定する。不足があり、推測で埋めると意味が変わる場合だけユーザーへ質問する。
5. GitHubのIssue検索で、タイトルと特徴的なエラー語を使ってopen Issueの重複を確認する。既存Issueが同じ現象を扱う場合は、新規起票せずリンクを返す。別Issueとして起票する明示的な理由がある場合だけ続行する。
6. 事実、推測、未確認事項を分けて本文を作る。トークン、Cookie、秘密値、個人情報、不要な巨大ログを含めない。
7. ユーザーが「起票」「作成」「公開」まで明示した場合だけ、接続済みGitHubツールを優先してIssueを作成する。利用できなければ、認証済みのGitHub CLIを使用する。どちらも利用できなければ本文をドラフトとして返し、作成済みと表現しない。
8. `bug`ラベルが存在する場合は付与する。ラベルが存在しない場合はIssue作成を優先し、未付与であることを報告する。
9. 作成後にIssue番号、タイトル、状態、URLを再取得して確認し、URLを返す。

## 品質基準

- タイトルだけで影響する機能と現象を判別できる。
- 再現手順を第三者が順番に実行できる。
- 期待する動作と実際の現象を混同しない。
- 原因が未確定なら断定せず、仮説として区別する。
- 実行していない検証を成功済みと書かない。
- Issueを作成した状態とドラフトだけの状態を区別する。

## 出力

- 重複Issueがある場合: 重複候補のURLと判断理由
- 起票した場合: Issueタイトル、番号、URL、付与したラベル
- 起票できない場合: 完成したドラフト、ブロッカー、必要な次の操作
