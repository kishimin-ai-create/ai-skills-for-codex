# Explain xUnit Test

指定されたxUnitテストを、コードから確認できる事実に基づいて日本語で説明する。

## 調査手順

1. 指定されたテストファイルを全文読む。
2. `using`、namespace、テストクラス、属性、fixture、helperを特定する。
3. テストが参照する本番型と、理解に必要な直接の実装だけを読む。
4. テストプロジェクトの`.csproj`を確認し、xUnitや関連ライブラリの前提を特定する。
5. リポジトリ内に仕様、ADR、テスト規約がある場合は、対象テストへ直接関係する箇所だけを読む。
6. テストをSmall、Medium、Largeのどれとして扱うか、依存範囲から判断する。リポジトリ固有の分類を優先する。

説明だけを求められた場合は、ファイルを変更せず、テストやビルドも実行しない。実行結果、修正、レビューを求められた場合だけ、その追加作業を行う。

## 説明の観点

### ファイル全体

- 何をテストするファイルか
- 対象となるバックエンド層と公開契約
- 外部依存、fixture、mock、stubの有無
- テスト間で共有される準備処理

バックエンドの依存方向を踏まえ、Model、Service、Port、Adapter、Controllerのどの境界を検証しているかを示す。実装詳細ではなく、利用側から観測できる振る舞いを中心に説明する。

### 各テストケース

テストごとに次を説明する。

1. テスト名を自然な日本語へ訳す。
2. 検証したい振る舞いを一文で述べる。
3. Arrange、Act、Assertへ分解する。
4. 各Assertionが何を保証するかを説明する。
5. 失敗した場合に疑う契約違反を述べる。

テスト名が`Subject_Action_WhenCondition_ExpectedResult`などの形式なら、Subject、Condition、Expected Resultを分けて説明する。

### xUnit構文

使用されているものだけを説明する。

- `[Fact]`: 固定された1ケース
- `[Theory]`: 複数データで同じ振る舞いを検証
- `[InlineData]`、`[MemberData]`、`[ClassData]`: Theoryへ渡すデータ
- `Assert.*`: 期待値と観測値の比較
- `IClassFixture<T>`、`ICollectionFixture<T>`: fixtureのライフサイクルと共有範囲
- `Fact.Skip`または`Skip`: 実行されないテストと、その理由
- `async Task`: 非同期処理の完了や例外を待って検証

一般的なxUnit解説を長く書かず、対象コードでの役割に限定する。

## 出力形式

次の順で、必要な項目だけを簡潔に出力する。

```markdown
## 概要

## ファイルの構成

## テストケース

### `<test method name>`

- 日本語訳:
- 目的:
- Arrange:
- Act:
- Assert:
- 保証する契約:

## xUnit構文

## 本番コードとの関係
```

短いファイルでは見出しを減らし、説明がコード本体より過度に長くならないようにする。

## 正確性

- コード、仕様、実行結果を混同しない。
- コードから断定できない意図は「推測」と明記する。
- スキップされたテストを成功済みとして扱わない。
- mockの呼び出し検証を、利用者向けの最終結果と同一視しない。
- `Assert`が実際に検証していない振る舞いを保証済みと説明しない。
- テストの不足や改善案は、ユーザーがレビューも求めた場合だけ提示する。
- 行番号を示す場合は、読み取った実ファイルの行番号を使用する。
