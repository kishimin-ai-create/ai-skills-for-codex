# ディレクトリ構成と競合の調査

調査依頼では、ファイル移動や設定変更を始めず、実際の解決経路を確認する。

1. リポジトリルート、各アプリのルート、作業ディレクトリを特定する。同名の`app`が別のアプリルートに存在するだけでは競合としない。
2. backend・frontend・共有schemaについて、エントリポイント、依存定義、ビルド対象、import/export、生成物の出力先を追う。
3. 症状に関係する設定だけを確認する。例としてworkspace境界、TypeScriptのinclude/excludeとalias、bundlerのalias、バックエンド言語のパッケージ探索がある。採用されていないツールは前提にしない。
4. エラーと設定・参照先の対応から、名前の重複、モジュール解決、責務の重複、生成先の衝突を区別する。設定値が実際に重なる証拠なしに競合と断定しない。
5. 確認できた現在構成、問題の根拠、必要なら最小の移行案を示す。既存構成が正常ならその結果も明示する。

共有schemaへ移す提案では、誰が使う契約か、実行時依存を共有してよいか、生成元と生成先のどちらが正本かを確認する。フォルダ名を揃えることだけを理由に抽出しない。

変更を依頼された場合は、参照、alias、ビルド・テストの対象、生成先を一緒に追跡する。利用中のリポジトリで定義された検証を使い、ディレクトリツリーが整っただけで移行完了としない。
