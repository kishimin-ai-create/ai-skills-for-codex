# TechBlog Diary

一連の作業（複数コミット、複数の変更、時には複数日）を、TechBlogリポジトリ配下に日付単位の作業日誌としてまとめる。読者は将来の自分自身であり、目的は「何を・なぜ・どう検証したか」を後から再構成できるようにすることである。

似た役割を持つ他の仕組みとの違いを先に押さえる。

- **write-articleスキル**: 1つのトピック・1つの教訓に絞った技術記事を`tech_blog`リポジトリ配下へ連番で残す。今回のスキルとは保存先リポジトリも構成も異なる。
- **work-summary-agent**: 対象リポジトリ自身の`diary/YYYYMMDD.md`に英語で完了・未完了を短く記録する。プロジェクト内部向けの短い引き継ぎメモであり、TechBlogという別リポジトリへの詳細な日本語日誌ではない。
- **本スキル**: 保存先はTechBlogリポジトリ。1日（または一連の作業セッション）で起きた複数の変更・調査・検証をまとめて振り返る、詳細な日本語の日誌を書く。

## 保存先

`$HOME\Desktop\programming\TechBlog\<category>\<repository_name>\<YYYYMMDD>\<YYYYMMDD>.md`

- `<repository_name>`: 作業対象リポジトリのフォルダ名（例: `pi-lab`）。
- `<category>`: TechBlogリポジトリ直下のカテゴリフォルダ。既定は`app`（Webアプリ・プロダクトのリポジトリ向け）。対象リポジトリがSQL・Git操作・GitHub運用など別カテゴリの話題に強く寄る場合は、`ls`でTechBlogルート（`ai`, `api`, `app`, `db`, `git`, `github`, `programming`, `python`, `regex`, `sql`, `ui`など）を確認し、最も近いカテゴリをユーザーに確認してから使う。判断に迷ったら`app`を提案する。
- `<YYYYMMDD>`: 日誌が対象とする作業の代表日（複数日にまたがる場合は最終更新日、または区切りの良い日）。

同じ日付のファイルが既に存在する場合は、上書きしない。既存記事の末尾に、明確な区切り（`---`と見出し）を入れて追記するか、対象期間が実質的に地続きであれば該当セクションを更新する。どちらにするかは既存記事の内容を読んでから判断し、ユーザーに確認する。

## 執筆前に確認すること

1. **対象範囲**: 今回の日誌が対象とする作業はどこからどこまでか（今日のセッション全体か、特定のトピックだけか）。会話履歴に既にコミット・変更ファイル・検証結果があれば、そこから抽出してユーザーに確認する形で進める。
2. **保存先**: 上記の`<category>`と`<repository_name>`、既存ファイルへの追記かどうかをユーザーに確認する。
3. これ以外の書き方の方針（事実と推測の区別、根拠の付け方など）は、[write-articleスキル](../write-article/SKILL.md)の手順・スタイルガイド・レビューchecklistにそのまま従う。本スキルは「TechBlogの日誌という媒体に何を書くか」の型を定義し、書き方そのもの（FACT/INFERENCE/PROPOSALの区別、根拠の追跡可能性、秘密情報の扱いなど）はwrite-articleの規律を再利用する。

## 記事の型

`20260806.md`・`20260807.md`（`TechBlog/app/pi-lab/`配下の既存日誌）で使われている型を踏襲する。

```markdown
# <対象システム名>：<この期間の作業テーマ>

## 結論

- 状態: 完了 / 部分完了 / ブロック
- 対象期間: <開始日>〜<終了日>（1日なら単日でよい）
- 対象: <対象コンポーネント・機能>
- 結果: <この期間で何が達成されたか、1〜2文>

<この日誌全体の要約を2〜4文>

## 作業前の課題

<この作業を始める前に何が問題だった／未整備だったか>

## <日付>：<その日のテーマ>

<変更の背景・原因調査・対応内容。複数日にまたがる場合は日付ごとに見出しを分ける>

```<言語>
<再現に必要な最小限のコード差分>
```

関連コミット:

- `<hash> <コミットメッセージ1行目>`

## 変更ファイル

| ファイル | 目的 |
| --- | --- |
| `path` | 何のために変えたか |

## 検証

| コマンド | 結果 | 確認内容 |
| --- | --- | --- |
| `command` | pass / fail / not run | 何を確認し、失敗ならどう切り分けたか |

## 事実・判断・未確認事項

- FACT: コマンド出力・ファイル・テスト結果から直接確認できること。
- INFERENCE: FACTから導いた判断。
- ASSUMPTION: 未確認で、採用理由と確認方法を併記する。

## 未完了・リスク

<残っている作業、解消していないリスク>

## 次のアクション

1. <具体的な次の一手>

## 参考

- ADRへの参照（関連する意思決定があれば）
- 外部ドキュメントへのリンク
```

「対象期間」が複数日にまたがるセッションを書く場合は、「## <日付>：<テーマ>」の見出しを日付ごとに繰り返す（`20260806.md`の2026年8月4日〜6日の3セクション構成を参照)。単日の作業なら、この日付見出しを省略し「## 対応」のような単一見出しにしてよい。

## 完了条件

- Markdownファイルが実際に保存されている（保存前に「作成済み」と報告しない）。
- TechBlogのリポジトリルート、`origin`、現在ブランチ、upstream、差分を確認している。
- 日誌と必要な訂正だけをstageし、`git-rules`に従う`docs:`コミットを作成している。既に正しくコミット済みなら重複コミットしない。
- `main`などの共有ブランチへ直接pushしていない。共有ブランチ上なら`docs/<short-description>`形式の作業ブランチを作成している。
- 作業ブランチと同名のremote refを明示してforceなしでpushし、ローカルHEADとremote branchのSHA一致を確認している。
- 保存したファイルパス、対象範囲、根拠（コミットハッシュ、実行したコマンドと結果）、push先、未確認事項をユーザーに報告する。
- 既存の同日ファイルを上書きしていない。

pushはTechBlogの日誌公開に限定して明示的に許可された処理である。題材となったリポジトリや共有ブランチへpushしてはならない。push失敗またはSHA不一致の場合は、公開済みと報告しない。
