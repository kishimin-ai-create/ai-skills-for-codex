# Manage Release Version

何の番号を更新するかと、なぜその番号になるかを先に特定する。アップロード回数と製品バージョンを同一視しない。

## 採番根拠

- 対象成果物、現在値、管理元、参照箇所を調べる。パッケージ、APIの表示値、コンテナタグ、リリースタグ、内部ビルド番号は、それぞれ別の管理対象になり得る。
- 既存のリリース履歴、採番規則、変更差分、公開済み範囲を確認する。ユーザーが指定した番号と規則が矛盾する場合は理由を示し、更新前にその判断を解決する。
- SemVerなどの規則は、そのプロジェクトが採用している場合に適用する。破壊的変更の有無をコミットのtypeや変更行数だけで判断せず、利用側への影響を見る。
- 「6回目のアップロードだから1.0.5」のような説明には、初期値・増分規則・失敗した公開の扱いという根拠があるか確認する。規則不明なら推奨案と未確定事項を示す。

## 更新・取消

- 依頼が妥当性確認だけならファイルを変更しない。更新依頼なら、番号の管理元と同じ製品番号を参照する箇所だけを変更する。
- ロックファイルなどの生成物は、既存の生成コマンドと更新範囲を確認する。番号更新に無関係な依存更新を混ぜない。
- 自動採番がある場合は管理元を優先し、生成された値と手書きの重複宣言を増やさない。タグの作成やパッケージ公開は、番号の編集とは別の操作として扱う。
- 最新の「更新しない」「取り消して」という指示を優先する。自分の未公開差分を特定して番号変更だけを戻し、ユーザーの既存変更を含むファイルを丸ごと復元しない。
- 公開済み番号や共有タグの取消は、ローカル編集の巻戻しと区別する。既存の配布物を削除したり、共有履歴を書き換えたり、公開済み番号を別内容へ再利用したりしない。

## 確認と報告

管理元と同じ番号であるべき参照箇所の整合、差分、既存のビルド・テストを確認する。APIなど実行時の番号が対象なら、可能な環境で表示値も照合し、設定値だけの確認と区別する。

現在値、提案値または指定値、採番理由、変更・取消した箇所、ローカル検証、公開の実施有無を報告する。別管理のビルド番号や依存バージョンを揃える必要はない。
