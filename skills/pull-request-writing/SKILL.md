# Pull Request Writing

レビュアーが変更理由、実装範囲、検証結果、残存リスクを短時間で確認できるPRを作成する。確認できない情報を推測で補わない。

## 責務境界

- PRタイトルと本文を作成し、依頼に応じてローカルへ保存する。
- ユーザーが明示的にPR公開まで依頼した場合だけ、既にリモートへ存在するブランチからPRを作成する。
- コード、テスト、設定、ADR、Git履歴を変更しない。
- `git push`を実行しない。ブランチが未公開なら、PRを公開せず必要な操作を報告する。
- PRを作成した事実と、本文ドラフトを保存しただけの状態を区別する。
- 呼び出し元Agentにより書き込みや外部操作が禁止されている場合は、その境界を優先する。

## 1. 対象範囲を確定する

1. 適用される`AGENTS.md`、関連ADR、仕様、Issueを読む。
2. `git status --short --branch`とリモート設定を確認する。
3. ユーザー指定のbase/headを優先する。指定がなければ追跡ブランチとリモートのデフォルトブランチから候補を確認する。
4. 比較範囲を確定し、`git log --oneline <base>..HEAD`、`git diff --stat <base>...HEAD`、`git diff --name-status <base>...HEAD`、完全なdiffを読む。
5. コミット済みの変更と未コミット変更を分離する。通常のPR本文には、実際にheadブランチへ含まれる変更だけを書く。

baseを一意に確定できず、候補によって内容が変わる場合はユーザーへ確認する。Issue番号、関連URL、要件を推測しない。

## 2. テンプレートを適用する

最初にリポジトリルートの`.github/pull_request_template.md`を探す。存在する場合は次を守る。

- 見出し、順序、チェック項目を維持する。
- HTMLコメントを執筆指示として読み、要求された情報を対応する節へ書く。
- 確認済みの項目だけを`[x]`にする。未確認項目を完了扱いにしない。
- 該当しない節はテンプレートの指示に従う。指示がなければ`該当なし`と理由を短く書き、見出しを削除しない。
- 複数テンプレートがある場合は、ユーザー指定または変更種別に一致するものを選ぶ。選択できなければ確認する。

テンプレートが存在しない場合は、次の順序を使う。

```markdown
## Title

<PR title>

## Summary

## Related Tasks

## What was done

## What is not included

## Impact

## Testing

## Notes
```

## 3. 根拠から本文を書く

- タイトルは変更の主目的を1つだけ表し、リポジトリの言語と命名規則に合わせる。
- Summaryでは、変更の背景と利用者または開発者に可能になったことを説明する。
- What was doneでは、重要な変更を責務や挙動の単位でまとめる。ファイル一覧をそのまま転記しない。
- What is not includedでは、明示的に除外した範囲だけを書く。
- Impactでは、利用者向け挙動、互換性、運用、データ、セキュリティへの影響を差分から確認できる範囲で書く。
- Testingでは、実行したコマンドと結果だけを書く。未実行なら理由を明記し、成功したと表現しない。
- UI変更では、確認可能なスクリーンショット、VRT、アクセシビリティ結果を記載する。存在しない成果物を作ったことにしない。
- 不明な必須情報は`TBD（根拠未確認）`とし、何を確認すべきかを添える。
- 秘密情報、トークン、個人情報、巨大なログを含めない。

## 4. ドラフトを保存する

ユーザーが保存先を指定した場合はその場所を使う。指定がなければ`pull-request/<title-slug>.md`へ保存する。

- ファイル名は短いkebab-caseとし、ファイルシステムで無効な文字を除く。
- 保存後に、テンプレートの見出し、順序、チェック項目が保たれていることを確認する。
- diff、コミット、検証結果と本文を照合し、誇張や取りこぼしを修正する。
- ドラフトを自動でコミットしない。適用されるGit規則またはユーザーの明示指示に従う。

## 5. 明示された場合だけPRを公開する

PR公開を依頼された場合は、次をすべて満たすことを確認する。

1. GitHub CLIの認証が有効である。
2. headブランチがリモートに存在し、PR対象コミットを含む。
3. base、head、タイトル、本文、draft状態を確定している。
4. 同じbase/headの既存PRがない。

条件を満たす場合だけ、本文ファイルを指定して`gh pr create`を実行する。作成後は`gh pr view --json url`でURLを確認し、そのリンクを返す。条件を満たさない場合はPRを作成せず、不足している前提を具体的に報告する。

## 完了条件

- 対象base/headと比較範囲が明確である。
- リポジトリのPRテンプレート、または標準構成に準拠している。
- 変更目的、実装範囲、対象外、影響、検証が観測可能な事実と一致している。
- 未確認事項と未実行テストが明示されている。
- 保存先または作成済みPRのURLと、参照した根拠を報告している。
