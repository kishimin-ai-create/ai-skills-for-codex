# APIの型・実行時Schema・生成仕様を照合する

対象ハンドラー、使用中のSchema、上流レスポンス、生成仕様、利用側コードを実ファイルから追う。プロパティ名だけでなく、ステータス、Content-Type、本文形式を同じケースで照合する。

## 型チェックを通る理由

- 外部JSONの型は使用中のライブラリと版で確認する。JSONを読むだけで実行時検証が済んだとは扱わない。
- 境界では未検証値を`unknown`として扱い、既存のSchemaまたは型ガードで検証してから使う。型アサーションで整合したように見せない。
- Schemaがドキュメント生成専用なのか、ハンドラーの戻り値の型へ接続されているのか、実行時にも検証されるのかをそれぞれ確認する。
- 「型エラーが出ない」理由は、`any`の伝播、戻り値型との未接続など、実際に確認できた接続関係で説明する。フレームワーク名だけで検査能力を断定しない。

## 照合するケース

| ケース | 確認すること |
| --- | --- |
| JSON成功 | 実際のキー・値の型と成功Schemaが一致するか |
| JSON失敗 | `error`と`message`などのキー、HTTPステータスが失敗契約と一致するか |
| 画像などのバイナリ成功 | 本文が生のバイト列かJSONオブジェクトか。生成仕様も同じ形式か |
| 上流API失敗 | 成功ステータスと成功Content-Typeを付けてエラー本文を返していないか |

バイナリ化する前に上流の成功・失敗を分岐し、失敗時は既存のエラー変換契約に従う。OpenAPIの表現は採用バージョンに合わせ、生の画像本文を架空のJSONラッパーとして記述しない。

修正を依頼された場合は、境界での検証と利用側から観測できるステータス・本文・Content-Typeを既存のテスト手段で確認する。生成仕様との照合も行い、手書きSchemaだけを見て完了しない。契約を変更する必要があるときは、実装の誤りと契約変更を区別する。
