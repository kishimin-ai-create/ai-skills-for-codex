# 型によるテスト駆動開発

型を制約の記述・検証・違反報告に使い、利用側から必要な抽象を発見する。コンパイラーまたは型チェッカーのフィードバックを設計の入力にする。

## 適用範囲

適用する。

- 静的型検査を利用できる言語で、API、ドメインモデル、関数シグネチャ、依存境界を追加または変更する。
- 利用側が必要とする操作やデータの関係を、型として設計したい。
- 具象実装への依存を抽象へ向け、既存利用側を壊さず実装を追加できる境界を作りたい。

適用しない。

- 実行時の値、外部I/O、副作用、性能、画面表示など、型検査だけでは判定できない振る舞いを検証する。
- 型検査のない言語や、対象リポジトリに実行可能な型チェックまたはコンパイル手段がない。
- 既存型の単純な名前変更など、利用側から設計を発見する余地がない機械的変更だけを行う。

実行時の振る舞いには `tdd` を併用する。型検査がGreenでも、振る舞いの正しさは証明されない。

## 事前確認

1. リポジトリに定義された型チェックまたはコンパイルコマンドを特定する。コマンドを推測しない。
2. 変更したい利用シナリオを小さなリストにする。型名の候補ではなく、呼び出し、生成、受け渡しなど利用側の要求を書く。
3. 一度に扱うシナリオを一つだけ選ぶ。
4. 型で保証する制約と、実行時テストで保証する振る舞いを分ける。

## Red: 型より先に利用側を書く

選んだシナリオを表す最小の利用側コードを書く。必要な型、メンバー、引数、戻り値、ジェネリック制約は、まだ存在しないか現在の要求を満たさない状態にする。

実際に追加する呼び出し側を優先する。型検査専用のコードを使うのは、リポジトリにコンパイルテスト用の置き場所と実行方法が既にある場合に限る。Redのためだけの未使用サンプルをプロダクションコードへ残さない。

型チェックまたはコンパイルを実行し、次を確認する。

- 失敗が、意図した型の未定義または型契約の不一致による。
- 構文エラー、設定不備、依存関係の欠落など、別の原因による偽のRedではない。
- 利用側コードが実装詳細ではなく、呼び出し側が必要とする契約を表している。

Redを作るために、既存コードを意図的に壊したり、不要な型検査専用APIを公開したりしない。

## Green: 最小の型を定義する

意図した型エラーがなくなる最小の型定義を追加する。

- Redで示した利用方法に必要な契約だけを表す。
- 将来使うかもしれないメンバー、型パラメーター、継承階層を先回りして追加しない。
- `any`、無制約な動的型、型アサーション、警告抑制、過度に広い型でエラーを隠さない。
- 実行時実装まで必要な言語では、コンパイルに必要な最小限を越えて振る舞いを作り込まない。振る舞いは通常のTDDで進める。

同じ型チェックまたはコンパイルを再実行し、対象の型エラーが消えたことを確認する。既存の型検査もすべてGreenでなければならない。

## Refactor: 型の設計を調整する

Greenを維持しながら、利用側と型定義の両方を見て設計を改善する。

- 名前がドメイン上の役割と制約を表しているか。
- 不正な状態を表現できない型にできるか。ただし、外部入力の実行時検証は省略しない。
- 型が具象実装ではなく、利用側に必要な最小の抽象を表しているか。
- 変動しやすい実装への依存を型境界の内側へ閉じ込められているか。
- 型を満たす新しい実装を、既存利用側の修正なしで追加できるか。
- 型パラメーター、共用体、継承、変性などが複雑さに見合っているか。

調整のたびに型チェックを実行する。実行時テストが存在する場合は、それもGreenに保つ。新しい利用シナリオが見つかったらリストへ追加し、次の小さなRedへ進む。

## コンパイル失敗を契約として残す場合

「このコードは型検査を通らないこと」自体が回帰防止に必要で、リポジトリにコンパイル失敗テストの仕組みが定義されている場合だけ、その仕組みで負の型ケースを残す。専用ツールやスナップショット形式を勝手に導入しない。

診断メッセージ全文へ過度に結合せず、可能ならエラーの位置や分類など、リポジトリで安定して検証できる契約を使う。

## 完了条件

- 利用シナリオのリストが空になっている。
- リポジトリ既定の型チェックまたはコンパイルが成功している。
- 型で保証する制約と、実行時テストで保証する振る舞いの境界を説明できる。
- 型エラーを隠すためだけの逃げ道を追加していない。
- 実行時の変更を伴う場合は、`tdd` のテストと検証も成功している。
