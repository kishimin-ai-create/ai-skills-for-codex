# Integration Test Strategy

単体テストと統合テストの責務を分け、統合テストがどの実際の結合を保証するかを明確にする。統合テストは単体テストではなく、特にシステムがDB・外部APIなどのプロセス外依存と統合された状態でどう機能するかを検証する。

## 他のSkillsとの境界

- 振る舞いのケース分解は `test-case-design`、具体的なテストコードは `test-patterns` を使う。
- unit / integration / E2E等のテスト種別とSmall / Medium / Largeのサイズを混同しない。サイズは実際の依存範囲で `test-sizes` と適用先の規則に従って判断する。
- TDDの実装順序は `tdd`、Acceptance Testの作成・保護は `atdd` に従う。
- 学派、テスト技法、4本柱などテスト品質全般の判断には `test-design-quality` を使う。

## 境界と検証対象を決める

1. 対象コードが純粋なドメインモデル／アルゴリズムか、外部との通信を担うコントローラー／アダプターかを確認する。
2. プロセス外依存と統合された実際の経路でしか証明できない契約を列挙する。例: DBへの保存・読み出し、トランザクション、HTTP本文・ヘッダー・ステータス、外部サービスとの通信。
3. 外部I/Oなしで決まる値変換やアルゴリズムは主に単体テストで検証し、同じ変換を広い統合テストで重複させない。
4. 外部I/Oや接続設定、シリアライズ、永続化など境界を通ることで初めて観測できる契約は、その境界を実際に通す統合テストで検証する。内部モックだけで統合が成立したと判断しない。
5. コントローラーの統合テストは広いコード範囲と実際の結合を検証できるが、環境準備や実行コストが増える。実行時間・安定性・準備と保守の費用を含めて補完範囲を決める。

統合テストは一般に退行への保護とリファクタリング耐性を得やすく、単体テストはフィードバック速度と保守のしやすさを得やすい。この比較は傾向であり、テストの境界・環境・設計によって逆転し得る。自動的な優劣判定にしない。

## 実行順序と独立性

初期方針では統合テストを1ケースずつ直列実行する。共有DB、外部サービス、テストデータの分離を準備・維持する費用が、並列化で得る時間短縮に見合わない場合が多いためである。

並列化する場合は、少なくとも次を確認し、利益が分離の費用を上回る根拠を持つ。

- 各ケースがDB、外部サービス、ポート、ファイル、識別子など競合する資源を独立に使う。
- テストデータの初期化・後片付けが他ケースへ影響しない。
- 並列実行時にも失敗が再現可能で、環境・データ競合による揺らぎがない。
- CI全体の時間短縮が、分離機構の実装・運用コストを正当化する。

直列実行でもテストケース間の依存を許さない。各ケースを初期化された状態から実行でき、単独・任意順でも結果が変わらないようにする。共有状態、fixture、cleanup、環境分離を点検し、前のケースが残した状態を次のケースの暗黙の入力にしない。

## 例外と適用先の規則

完全に隔離された専用環境やデータ分離が既にあり、並列化の利益が明確に大きい場合は並列実行を選べる。選択理由と独立性の根拠を記録する。直列を目的化したり、ケース間依存を正当化したりしない。

統合か単体かというテスト種別とSmall / Medium / Largeという実行サイズは別軸である。E2Eを含め、サイズは利用する依存範囲で判断する。ファイル名、テスト配置、runner、CI並列度に既存規則があれば、一般的な推奨より適用先の設定とADRを優先する。共有Skillの現行判断ではADR-0004がサイズ名、ADR-0032が純粋な変換とHTTP輸送境界の分離、ADR-0044がテスト種別とサイズの分離を定めている。
