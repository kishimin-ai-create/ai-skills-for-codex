# Bounded Unicode Text Validation

Unicodeの利用者向け文字数契約を保ちながら、未信頼入力の検証処理量を制限する。

## 手順

1. 入力境界、公開される最大書記素数、エラー優先順位を仕様とテストから確認する。
2. 現在の実装が入力全体を走査・配列化するか、長大なASCII入力で割り当て量または処理時間を計測する。
3. 修正前に回帰テストを追加し、失敗を確認する。実時間timeoutだけに依存せず、割り当て量や列挙回数など決定的な観測値を優先する。
4. 業務上限とは別に、現実的なUnicode表現へ十分な余裕を持つUTF-16コード単位の防御上限を定める。
5. 防御上限を超えた入力を先に拒否し、書記素列挙は業務上限を1つ超えた時点で終了する。
6. 絵文字のサロゲートペア、結合文字、境界値、長大入力、既存のエラー優先順位を検証する。
7. 対象テスト、全テスト、ビルド、カバレッジを実行し、修正前後の観測値を報告する。

## 判断ルール

- 書記素単位の契約がある場合、`string.Length`だけを業務上の文字数として使わない。
- 小さな上限との比較のために、未信頼入力全体の書記素開始位置を配列化しない。
- 防御上限は業務上限と区別し、通常のUnicode入力を拒否しない根拠とトレードオフを記録する。
- HTTPリクエスト全体の上限とDomain値の上限を混同しない。必要なら両方を独立して設計する。
- 共通化はエラー順序や型ごとの契約を隠さない範囲に限定する。

## 完了条件

- 修正前の問題を再現している。
- 過大入力の検証処理量が明示的な上限で制約されている。
- 書記素単位の既存契約とエラー優先順位が維持されている。
- 回帰テストが修正前に失敗し、修正後に成功している。
- 残存リスクとして、防御上限を超える極端な単一書記素を拒否することを明記している。
