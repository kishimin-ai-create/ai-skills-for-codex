# Issue Loop

## 目的

Issueに書かれた受け入れ条件を、マージ済みのコードへ変換する。1件を完遂してから次の1件へ進み、対象Issueが尽きるまで繰り返す。

進捗はGitHubとリポジトリに残す。会話履歴には残さない。無人実行では、前回のセッションはもう存在しないためである。
状態を会話からしか復元できないループは、セッションが切れた瞬間に再開できなくなる。それは無人実行が最も必要とする場面である。

この性質は、長い連続実行の中でも同じように働く。会話が伸びて文脈が要約されても、ステップ0をやり直せば現在地を取り直せる。
**前のIssueで何をしたかを記憶に頼って次へ進んではならない。** 各サイクルはステップ0から始める。

## 自律実行

**このループの実行中、判断を止めてユーザーへ確認を求めてはならない。**

呼び出された時点で、以下はすべて許可されている。確認は不要である。

- ブランチの作成、コミット、push
- PRの作成、更新、コメント投稿
- CIが全て成功したPRのsquash merge
- マージ済みブランチの削除
- Issueのクローズ、トラッキング用チェックボックスの更新
- 記事と日誌の作成、そのブランチへのpush

判断に迷う点が出た場合、確認を求めるのではなく、**記録した前提のもとで進め、最後の報告に前提を明示する。**
判断できないほど情報が欠けている場合だけ、停止条件に従って止まる。止まることと訊ねることは違う。

例外は次のみである。`main`への直接push、共有ブランチへのforce push、Issueの削除、履歴の書き換え。
これらは許可の範囲外であり、確認を取っても行わない。

このSkillは`git-rules`が言う「明示的に許可された別のワークフロー」である。

## モデルの割り当て

トークンは有限である。判断の質が結果を左右する工程だけに上位モデルを使い、量をこなす工程は下位モデルに任せる。

| 工程 | 担当 | モデル | 理由 |
| --- | --- | --- | --- |
| AT設計 | `atdd-agent` | opus | 誤ったATは以降のすべてを汚染する |
| 実装 | `tdd-agent` | sonnet | 最もターン数が多い。ATが正しければ判断の幅は狭い |
| テストレビュー | `test-review-agent` | opus | 見逃した欠陥は検出されない |
| コードレビュー | `code-review-agent` | opus | 同上 |
| 修正 | `fix-*-agent` | sonnet | 原因が特定済みの作業 |
| PR本文 | `pull-request-writer-agent` | sonnet | 差分という根拠がある |
| コメント返信 | `review-response-agent` | sonnet | 分類と委譲が主 |
| ADR | `adr-writer-agent` | opus | 残す価値の判定を誤ると、読まれない記録が積み上がる |
| 記事・日誌 | `article-write-agent` / `work-summary-agent` | sonnet | 事実からの執筆 |

各Agentの定義に`model`が記録されている。呼び出し側で上書きしない。

トークンを節約するため、次を守る。

- Agentの出力は要約を受け取る。全文をこのセッションへ展開しない。
- ログやテスト出力は`tail`で必要な範囲だけ読む。
- 同じファイルを繰り返し読まない。

## 呼び出し側が与える入力

プロジェクト固有の値は、このSkillに書かず呼び出し側（定期タスクのプロンプトなど）が渡す。

| 入力 | 内容 | 省略時 |
| --- | --- | --- |
| リポジトリのパス | 作業対象の絶対パス | 現在の作業ディレクトリ |
| トラッキングIssue | 実行順を定義するIssue番号 | 後述の規則で探索する |
| 除外ラベル | 対象外とするラベル | 除外しない |
| 検証コマンド | 実行するローカル検証 | `package.json`等から検出する |
| マージ権限 | 自動マージの可否 | 不可として扱い、PR作成で停止する |
| 記事・日誌の出力先 | 保存先リポジトリまたはディレクトリ | 各Skillの既定に従う |
| 1回あたりの上限 | 処理するIssueの件数 | 尽きるまで続ける |

複数のリポジトリを対象にする場合、1回の実行で扱うのは**1リポジトリだけ**にする。
リポジトリをまたぐと、ツールチェーン、規約、ディレクトリ構成が切り替わり、直前のリポジトリの
前提を持ち込みやすい。対象の選び方は呼び出し側が指定する。

## 手順

### 0. 状態を確認する

会話履歴ではなく、リポジトリとGitHubの実態から判断する。

```sh
git status --porcelain
git branch --show-current
gh pr list --state open --json number,title,headRefName,isDraft
gh issue list --state open --limit 100 --json number,title,labels
```

次のいずれかに該当する場合は、新しいIssueを始める前にそれを解決する。

- **未コミットの変更がある** — 内容を確認する。前回の中断分なら続きから進める。判断できなければ停止して報告する。
- **未PRのコミットがある作業ブランチにいる** — そのコミットが対応するIssueを特定し、ステップ6から再開する。
- **draftのPRが開いている** — 上限に達して保留されたものである。再び手を付けず、保留として記録し、そのIssueは飛ばす。
- **オープンなPRにレビューコメントが付いている** — ステップ9から再開する。
- **完了済みなのにオープンなIssueがある** — 受け入れ条件を実コードと照合し、満たされているものをクローズする。
  **実コードとテストの存在を根拠にする。推測でクローズしてはならない。**

### 1. Issueを選ぶ

トラッキングIssueが与えられていれば、その本文のチェックリストに現れる`#N`の順に見る。
与えられていなければ、オープンなIssueのうち本文に`- [ ] #N`形式のチェックリストを持つものを探し、それをトラッキングIssueとして扱う。
見つからなければIssue番号の昇順にする。

最初に見つかった、次の条件をすべて満たすIssueを選ぶ。

- オープンである
- 除外ラベルが付いていない
- 本文に`## Acceptance criteria`がある

トラッキングIssue自身は選ばない。それは他のIssueの完了によって満たされる。

該当するIssueが無ければ、完了条件の確認（ステップ14）へ進む。

### 2. ブランチを作る

```sh
git switch main
git pull --ff-only
git switch -c <type>/<issue番号>-<kebab-caseの要約>
```

`<type>`は`git-branch-naming`に従う。機能追加は`feature/`、不具合修正は`fix/`である。

### 3. ATを固定する（Outer Red）

`atdd-agent`へ委譲する。Issue本文の`## Acceptance criteria`を受け入れ条件、`## Out of scope`を範囲外として渡す。

`atdd` SkillのIssue方式に従い、ACを`docs/ACCEPTANCE.md`へ複製しない。Issue本文が唯一の正である。

ACがATへ変換できる水準に満たない場合、**推測で補ってはならない。** 何が不足しているかを報告して保留する。
浅いATはATDDの失敗ではなく、要件の不足として現れる。

ATが未実装を理由に失敗することを確認し、`test:`でコミットしてSHAを記録する。

### 4. 内側のループを回す

`tdd-agent`へ委譲し、Red→Green→Refactorを1項目ずつ進める。

このフェーズで`acceptance/`を変更してはならない。各コミットの前に確認する。

```sh
git status --porcelain -- acceptance/
```

### 5. レビューする（PR作成前）

**このステップを飛ばしてはならない。** 実装した主体がテストを書いた場合、「通った」は弱い根拠にしかならない。
PRを出した後に見つかる欠陥は、CIを1周余計に回し、レビュアーの時間を使う。出す前に見つけるほうが安い。

テストとプロダクションコードは別々にレビューする。**テストが良くてもプロダクションコードが壊れている場合があり、その逆もある。**

必ず実施する。

| 対象 | 担当 | 適用するSkill |
| --- | --- | --- |
| テスト | `test-review-agent`（opus） | `review-tests-with-twada-principles` |
| プロダクションコード | `code-review-agent`（opus） | `engineering-principles`、`refactor-patterns` |
| 差分全体 | このセッション | `code-review` Skill |

変更が触れた領域に応じて追加する。触れていない領域のレビューは実行しない。時間とトークンを使うだけである。

| 変更が触れた領域 | 追加するレビュー |
| --- | --- |
| 認証、認可、秘密情報、入力境界、外部API | `security-review`、該当する`security-*` Skill |
| バックエンドの層構成、Repository境界、エラー変換 | `backend-patterns` |
| SQL、スキーマ、インデックス、トランザクション | `sql-anti-patterns` |
| React コンポーネント、状態、ルーティング | `frontend-components`、`frontend-state`、`frontend-routing` |
| ブラウザ保護、Cookie、CSP、CORS | `frontend-security` |
| UIコンポーネント、フォーム、動的な状態表示 | `a11y`、`human-interface-guideline` |
| 条件分岐の構造、状態や種別による表示切り替え | `react-branching-design` |
| Storybook のストーリー | `storybook-patterns` |
| 設計判断、代替案の比較、高リスクな変更 | `critical-review` |

指摘は`validate-review-findings`で選別する。**P1は次へ進む前に解消する。** 誤検出と判定したものは、その根拠を記録する。

修正は`fix-*-agent`（sonnet）へ委譲する。修正後、影響する検証を再実行する。

### 6. ローカルで検証する

呼び出し側が指定した検証コマンド、またはリポジトリで定義されているものを実行する。
存在しないコマンドを推測して実行してはならない。

**結果を出力として残す。** 「通った」と述べるだけにしてはならない。

続けて、AT確定コミット以降に`acceptance/`が変更されていないことを確認する。

```sh
git status --porcelain -- acceptance/
git diff --name-only <AT確定コミットのSHA>..HEAD -- acceptance/
```

どちらかが空でなければ、そのGreenは根拠にならない。停止して差分が生じた理由を報告する。

### 7. PRを作る

`pull-request-writer-agent`へ委譲して本文を作成し、PRを作成する。
リポジトリにPRテンプレートがあれば従う。本文にIssueへのクローズ参照（`Closes #N`）を含める。

ステップ5のレビューで解消した指摘と、誤検出と判定した指摘をその根拠とともに本文へ記載する。

```sh
git push -u origin <ブランチ名>
```

### 8. CIを待つ

```sh
gh pr checks <PR番号> --watch
```

全て成功したらステップ9へ進む。失敗したら次のように扱う。

1. 失敗したジョブのログを読み、原因を特定する。
2. `fix-test-agent`（テスト失敗）、`fix-lint-agent`（Lint・型）、`fix-agent`（その他）へ委譲する。
3. 修正をpushし、再度CIを待つ。

**自動修正は最大2回までとする。** 上限を超えたらPRをdraftへ変更し、失敗ログを記録する。
そのIssueは保留とし、`main`へ戻って次のIssueへ進む。draftのまま残すことが、人間への引き継ぎになる。

```sh
gh pr ready <PR番号> --undo
```

再試行に上限を置くのは、無制限の再試行が「緑にする」圧力になり、実装ではなくテストを弱める経路を開くためである。
その経路を塞ぐことがATDDの目的であり、ここで開いては意味がない。

### 9. Codexのレビューを受ける

CIが全て成功したら、PRへレビューを依頼するコメントを投稿する。

```sh
gh pr comment <PR番号> --body "@codex review"
```

コメントが付くまで待つ。取得はGitHub MCPまたは`gh`で行う。

```sh
gh pr view <PR番号> --json comments,reviews
```

**この往復は最大2周とする。** 1周は次の3つで構成される。

1. 新しいレビューコメントを読む。
2. `validate-review-findings`で妥当性を判定する。**指摘を鵜呑みにしない。** 誤りと判断したものは修正せず、根拠を返信に書く。
3. 妥当な指摘を`fix-*-agent`へ委譲して修正し、pushしてCIを待つ。再度`@codex review`を投稿する。

2周を終えた時点で残っている指摘は、返信で扱いを明示する。修正のために3周目へ進んではならない。
無限にレビューへ応じ続けることは、品質ではなく終わらないループを生む。

一定時間コメントが付かない場合は、待ち続けずステップ10へ進む。待ったことを報告に残す。

### 10. コメントへ返信する（マージ前）

**未返信のコメントを残したままマージしてはならない。**

`review-response-agent`へ委譲し、`github-address-pr-comments`を適用する。
各コメントを「修正した」「修正しない」のどちらかに分類し、**すべてに返信する。**

- 修正したものは、どのコミットで直したかを示す。
- 修正しないものは、なぜ不要と判断したかを根拠とともに書く。「後でやる」は理由ではない。Issueを立てて番号を示す。

解決済みのThreadはresolveする。

### 11. マージしてIssueを閉じる

マージ権限が与えられている場合にのみ実行する。加えて、**何がGreenを保証したか**で可否を決める。

| リポジトリの状態 | マージ |
| --- | --- |
| `pull_request`で動くCIがあり、全て成功した | する |
| `pull_request`で動くCIがあり、失敗が残る | しない。ステップ8の扱いに従う |
| CIが無いが、リポジトリに検証コマンドがあり、ローカルで全て成功した | する。PR本文に実行したコマンドと結果を記載する |
| CIが無く、検証コマンドも無い | **しない。** PRを開いたまま残し、人間へ引き渡す |

最後の行が重要である。検証する手段が1つも無いリポジトリでは、「通った」と言える根拠が存在しない。
そこで自動マージすると、ループは速く動いているように見えて、実際には検証していないコードを
main へ積み続ける。CIの整備自体がIssueとして存在するなら、それを先に通す。

```sh
gh pr merge <PR番号> --squash --delete-branch
```

squashで各コミットのWhyが失われるため、squashメッセージへ集約する。

マージ後、Issueがクローズされたことを確認する。`Closes #N`で自動クローズされなければ手動で閉じる。
トラッキングIssueのチェックボックスを更新する。

```sh
git switch main
git pull --ff-only
```

### 12. 判断を再利用できる形にする

このサイクルで下した判断のうち、次も同じ場面で参照されるものを記録する。
記録しなければ、同じ議論を次のサイクルでやり直す。

`assess-adr-candidate`を適用し、次の出どころから判断を集めて分類する。

- レビューで指摘され、修正方針として採用した判断
- Codexレビューで却下した指摘と、その根拠
- 実装中に検討して選ばなかった代替案
- 設定やゲートの変更（閾値、除外、CI構成、保護設定）

| 分類 | 扱い |
| --- | --- |
| 再利用可能な設計判断 | ADRを書く |
| 決定的で静的に検査できる規約 | Linterルールにする |
| 既存ADRで対応済み | 何もしない。該当するADR番号を報告に書く |
| このサイクル限りの事情 | 何もしない |

**すべてをADRやLinterルールにしてはならない。** 数が増えるほど1件あたりの重みが下がり、
やがてどれも読まれなくなる。増やすことではなく、読まれる状態を保つことが目的である。

#### ADRにするもの

`adr-writer-agent`（opus）へ委譲し、`adr-writing`を適用する。保存先は`$HOME/.codex/docs/adr/`で、
既存の連番の続きを使う。書く前に関連する既存ADRを確認し、重複や矛盾があれば新規作成ではなく改訂を選ぶ。

次をすべて満たす場合だけ書く。

- 別の選択肢が実在し、そちらを選ばなかった理由がある
- 将来、同じ判断を再びする場面がある
- コードを読んでも、なぜそうしたのかが分からない

「こう実装した」はADRではない。コードが既に語っている。**ADRが語るのは、そうしなかった選択肢である。**

#### Linterルールにするもの

`eslint-custom-rules`と`linter-driven-tdd`を適用する。ルールは対象リポジトリへ置き、**専用のPRを出す。**
実装のPRへ混ぜない。規約の変更はそれ自体がレビュー対象であり、機能の差分に紛れさせると誰も読まない。

次をすべて満たす場合だけ作る。

- 違反を機械的に判定でき、人の解釈が要らない
- レビューで繰り返し指摘している、または今後繰り返すと分かっている
- 違反例と準拠例の両方を書ける

`linter-driven-tdd`に従い、意図した違反がRedになることを確認してからルールを確定する。
**判断が要る規約をルールにしてはならない。** 誤検出が出るたびに抑制コメントで黙らせる運用になり、
やがて本当の違反も一緒に見えなくなる。ルールが信用を失うと、規約そのものが機能しなくなる。

### 13. 記事と日誌を書く

**1サイクルはここで終わる。記事と日誌を書かずに次のIssueへ進んではならない。**

作業の記録は、作業した直後にしか正確に書けない。後からまとめて書けば、判断の理由は思い出せず、
「何をしたか」だけが残って「なぜそうしたか」が落ちる。それはこのループが最も残したい部分である。

1. `article-write-agent`へ委譲する。`write-article`を適用し、独立した話題ごとに1記事とする。
   このサイクルで解決した問題、選ばなかった代替案、レビューで見つかった欠陥が題材になる。
   書くに足る題材が無ければ、無理に書かず「該当なし」と報告する。**水増しした記事は記録の価値を下げる。**
2. `work-summary-agent`へ委譲する。`techblog-diary`を適用し、完了・未完了・保留を区別して日誌へ追記する。

どちらも根拠のある事実だけを書く。検証していないことを成果として書いてはならない。

### 14. 次のIssueへ進む

対象Issueがまだ残っていれば、**ステップ0へ戻って次の1件を始める。**

このとき、前のサイクルの記憶を引き継がない。`main`は更新され、Issueは閉じられ、ブランチは削除されている。
現在地はすべてGitHubとリポジトリから読み直せる。読み直すほうが、覚えているつもりでいるより確実である。

対象Issueが尽きたら、除外ラベルを除く全Issueがクローズされていることを確認する。
トラッキングIssueの受け入れ条件を確認し、満たされていればトラッキングIssueもクローズする。

最後に、処理した全Issue、作成したPR、書いた記事と日誌、保留したIssueとその理由、
スキップした検証とその理由を報告する。

## 停止条件

停止の範囲は2段階ある。連続実行では、1件の行き詰まりで全体を止めない。
どちらの場合も、ユーザーへ確認を求めるのではなく、記録して進むか止まるかを自分で決める。

### そのIssueを保留し、次のIssueへ進む

理由を記録し、`main`をクリーンな状態へ戻してから次へ進む。保留したIssueは最後の報告にまとめる。

| 状況 | 扱い |
| --- | --- |
| 受け入れ条件が不足してATを書けない | Issueは変更せず保留する。推測で補わない |
| CI修正の上限を超えた | PRをdraftにして残す。ブランチは削除しない |
| Codexレビューの往復上限を超えても未解決の指摘が残る | 返信で扱いを明示し、必要ならIssueを立てる |

### 実行全体を止める

リポジトリの状態そのものが信頼できないため、次のIssueへ進んでも同じ結果になる。

| 状況 | 理由 |
| --- | --- |
| 実装フェーズで`acceptance/`が変更された | 保護が破れている。以降のGreenがすべて根拠にならない |
| `main`のpullが競合した | 以降のブランチがすべて誤った起点から分岐する |
| 未コミットの変更の素性が判断できない | 取り込んでよいか判断できない変更を、次の作業へ巻き込む |
| 同じIssueで2周続けて進捗が無い | 同じ失敗を繰り返している。原因を報告する |

## やってはならないこと

- ループ実行中にユーザーへ確認を求める
- 受け入れ条件を推測で補う
- テストを弱めて、または削除してCIを通す
- 検証を実行せずに「通った」と報告する
- PR作成前のレビューを飛ばす
- 未返信のコメントを残してマージする
- 判断の棚卸しと、記事と日誌を書かずに次のIssueへ進む
- 読まれないADRやLinterルールを数のために増やす
- 判断が要る規約をLinterルールにする
- Linterルールの変更を実装のPRへ混ぜる
- レビュー指摘を検証せずに鵜呑みにして修正する
- 1つのIssueが完了する前に次のIssueへ着手する
- 前のサイクルの記憶を根拠に現在地を判断する
- マージ権限が無いのにマージする
- `main`へ直接pushする
